Agent面试题：LangChain 和 LangGraph 有什么差异？分别适合构建什么类型 Agent？

一、面试题原文

面试官问：LangChain 和 LangGraph 有什么差异？分别适合构建什么类型 Agent？

初级回答（直接pass）：LangChain是链，LangGraph是图。

面试官真正想听的：不是名字上的区别，而是工程选型判断——什么时候用哪个？为什么？底层运行机制有什么不同？

二、痛点分析

痛点维度 具体表现
认知误区 很多人以为两者是替代关系，其实是互补关系
选型困惑 做Agent到底用LangChain还是LangGraph？新手容易纠结
工程落地难 简单任务用LangGraph是过度设计，复杂任务用LangChain会越来越乱
面试加分点 能讲出分层架构（组件层+编排层+观测层），比单纯说”链和图”高级很多

本质问题：不是”哪个框架更好”，而是”任务复杂度决定技术选型”。

三、核心概念对比

一句话定位

框架 定位 核心价值
LangChain LLM应用开发框架（组件层） 快速把LLM应用搭起来
LangGraph Agent编排运行时（编排层） 复杂流程如何稳定跑起来
LangSmith 观测评估平台（观测层） 全链路追踪、调试、评估

面试加分句：它们不是互相替代，而是同一套工程栈的分层。LangChain提供组件，LangGraph提供编排，LangSmith提供观测。

四、LangChain 详解

核心特点

  • 组件多、集成多、上手快
  • 提供模型、工具、检索器、提示词、Agent的高层抽象
  • 适合把LLM应用从零拼起来

典型适用场景

场景 说明
简单聊天机器人 流程固定，单轮或简单多轮对话
RAG问答系统 用户提问→检索文档→拼接Prompt→生成答案
简单工具调用Agent 调用1-2个工具就能完成任务
快速Demo验证 给老板演示效果，快速出原型

代码特征

  • 常见写法：create_agent，绑定模型和工具
  • 封装了默认流程，开发者不需要控制每一步
  • 偏线性链路：输入→处理→输出

五、LangGraph 详解

四大核心概念

概念 说明
State（状态） 共享状态，记录消息、任务、工具结果和中间变量
Node（节点） 执行逻辑单元，可以是模型调用，也可以是普通函数
Edge（边） 流程跳转，可以固定，也可以是条件分支（ConditionalEdge）
Reducer（规约器） 合并状态更新，特别适合并行节点的状态合并

核心能力

能力 说明
Checkpoint（检查点） 保存运行状态，中断后可从断点恢复，不用从头再来
持久化 长期任务的状态持久化存储
流式输出 支持节点级别的流式输出
人工介入（Human-in-the-loop） 流程可暂停，等待人工审批后继续执行

什么时候必须用LangGraph？

场景 原因
1. 流程有多个步骤 步骤多了，链式调用会越来越乱
2. 中间有条件分支和循环 需要if/else判断、重试循环
3. 需要人工审批或人工修改状态 高风险操作需要人工确认
4. 任务可能跑很久，需要保存进度 长任务中途中断，要能恢复
5. 失败后不能重头再来，要从checkpoint恢复 重跑成本太高

六、选型对比矩阵

维度 LangChain LangGraph
抽象层次 更高，封装更多 更低，控制更细
学习门槛 低，上手快 高，需要理解状态机
流程模型 线性链式（DAG） 循环状态图
状态管理 无状态，需手动传历史 原生共享状态管理
分支循环 支持有限 原生支持条件分支、循环
中断恢复 不支持 原生Checkpoint支持
人工介入 不原生支持 原生支持暂停/恢复
适合任务复杂度 低-中等 中-高
开发效率 高，快速出活 中等，需要设计状态图
可维护性 简单场景好，复杂场景乱 复杂场景清晰可控

七、选型口诀

简单用LC，复杂用LG

  • 组件集成用LC：接模型、接工具、做RAG、快速拼应用
  • 流程状态用LG：多步骤、长任务、人工审批、失败恢复

具体判断

业务场景 推荐方案
公司制度问答（RAG） LangChain ✅
单轮工具调用查询 LangChain ✅
客服处理Agent（分类→查库→判断退款→人工审批） LangGraph ✅
数据分析Agent（写SQL→执行→失败重试→分析→报告） LangGraph ✅
多Agent协作任务分配 LangGraph ✅
快速Demo给老板看 LangChain ✅

八、常见误区

误区 纠正
❌ LangChain就是链，LangGraph就是图 ✅ 不只是名字，本质是组件框架 vs 编排运行时
❌ 两者是替代关系，用了一个就不用另一个 ✅ 生产中通常组合使用：LangChain组件 + LangGraph编排
❌ 复杂项目直接上LangGraph ✅ 简单任务用图是过度设计，增加复杂度
❌ LangChain已经过时了 ✅ 垂直行业RAG场景依然是基石，没过时
❌ Agent出错了看模型回答就行 ✅ LangGraph要先看State对不对，再看Node执行，再看Edge分支，最后才看模型

九、面试标准回答模板

面试官您好，我是这样理解的：

第一，定位不同。LangChain更偏LLM应用框架，提供模型、工具、检索、提示词的高层抽象，核心是快速搭建应用。LangGraph更偏Agent编排运行时，用状态图管理多步骤、分支、循环、持久化和人工介入。

第二，能力侧重不同。LangChain优势是组件多、集成多、上手快，适合线性流程的RAG问答和简单工具调用。LangGraph优势是状态管理、条件分支、中断恢复、人工介入，适合复杂长任务。

第三，生产中通常组合使用。用LangChain的组件能力接模型、绑工具、做检索，再用LangGraph做流程调度和状态管理，最后配LangSmith做全链路观测。

选型上：简单RAG和单轮工具调用用LangChain更快；多步骤、长任务、需要人工审批和失败恢复的场景用LangGraph更稳。

十、延伸追问预测

可能追问 答题方向
LangGraph的State怎么设计？ 共享状态字典、Reducer合并、避免状态膨胀
怎么解决Agent死循环问题？ 设置递归深度上限、循环检测、超时退出
状态膨胀怎么处理？ 只传增量、子图拆分、定期清理历史
不用LangGraph，自己怎么实现状态机？ 节点+边+状态字典+Checkpoint序列化
LangChain版本更新快，升级踩过坑吗？ 封装底层、版本锁定、升级回归测试
Multi-Agent场景怎么选？ LangGraph做多Agent编排，注意分布式调度和锁机制
